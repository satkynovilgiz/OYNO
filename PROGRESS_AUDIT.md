# OYNO — Progress Audit

Generated by a full self-audit pass against the project's own spec, conventions,
and prior research. Methodology and an important caveat below — read that before
the findings, it affects how to read every status in this document.

## Methodology & a real limitation

This audit was asked to be structured "by spec section number, matching the
original OYNO spec document." **That document is not in this repository**, and
was not shared in the conversation that produced this audit. It's referenced
constantly by section number in code comments and in `games/RESEARCH_SUMMARY.md`
(confirming it exists and a prior session had it in full — e.g. Section 43's
"do not invent" rule, Section 46's task order), but nothing here checked it in,
and no README or docs/ folder points to where it lives externally.

What this audit *could* reconstruct, by grepping every `spec Section N` comment
already left in the codebase by prior sessions:

| Section | Topic (recovered from code comments) |
|---|---|
| 2 | Sign Up flow / guest mode |
| 3 | Explore location categories (Оюндар, Ашкана, ...) |
| 6 | Game intro / per-game host characters |
| 8, 11, 13, 14, 15, 16, 17 | Чүкө, Аркан тартыш, Жоолук таштамай, Жаа атуу, Кыз куумай, Beshbarmak, Cooking World (other dishes) |
| 43 | Cultural-accuracy / no-invent rule |
| 46 | Development task priority order |

Everything else (exact section numbers for Culture, Profile, Onboarding/Auth,
Home, the shared XP/achievement/economy systems, and the *exact* Section 46
task list) is **not recoverable from the repo**. This audit is therefore
structured **by feature area**, not by literal section number, with recovered
section numbers noted where I have them. If you have the source document, share
it and I'll re-key this file to match it exactly.

Everything below marked ✅ was actually run (`tsc --noEmit`, `jest`, or a
component I built and screenshotted earlier this session) — not just read. Where
I could only verify by reading code (the in-browser click-through was blocked
this session by a Chrome extension issue unrelated to the app — script injection
timing out tool-wide, on pages that worked fine earlier in the same session), I
say so explicitly rather than marking it ✅.

- **Locale file coverage is inconsistent across features, by design, not by
  accident** — worth knowing before treating gaps as bugs:
  - Home, GameIntro, CharacterSelect, Culture, Profile: real `t()` calls

    session that built Explore (matches how it treats location facts as
    Kyrgyz-sourced content), but it means Explore does not actually respect a

## 9. Shared systems (XP, achievements, daily challenges, notifications,
leaderboards, friends/social, economy)

❌ **None of these have real backing state.** Checked `src/store/` directly —
`useAppStore.ts` is the *only* Zustand store in the app and it holds exactly
two fields: `language` and `characterId`. Every XP bar, coin count, streak
counter, achievement badge, daily-challenge card, and quest-progress number
anywhere in Home/Games/Explore/Culture/Profile is **rendering a hardcoded mock
object** (`mockPlayer`, `mockProfile`, `exploreProgress`, `cultureProgress`,
etc.). Tapping "Алуу" (claim reward) on any card logs to the console and
changes nothing. There is no persistence layer at all — a full reload always
resets to the same mock numbers.

This isn't a defect in any single screen; it's that **no screen in the app is
backed by real app state beyond language/character selection.** Building this
(a real `useGameProgressStore` or equivalent, with AsyncStorage persistence,
that XP/coins/achievements actually read from and write to) is the single
highest-leverage foundational gap in the whole codebase — every "🟡 PARTIAL"
screen above becomes real the moment this exists, without changing much UI
code.

## Step 3 — build log

**Тогуз коргоол engine + tests** — `games/toguzKorgool/types/index.ts`,
`games/toguzKorgool/engine/index.ts`, `games/toguzKorgool/engine/index.test.ts`
(26 new tests, all passing). Follows the exact convention established by Беш
таш (pure functions, no React/UI dependency, `createInitialState` /
`startGame` / an `applyMove`-style function returning `{ state, result }`).
Implements everything RULES.md states as fact:

- 18-pit board (9 stones × 9 pits × 2 rows = 162 total), sowing one stone per
  pit in a single consistent direction, wrapping the full 18-pit ring.
- Capture rule: last stone landing in an opponent's pit with an even count
  sweeps that pit to the sower's kazan.
- Tuz: once-per-player declaration, blocked on the ооз pit and on mirroring
  the opponent's declared local position; any stone landing in a tuz pit
  (whether or not it's the last stone of the sow) is swept immediately to the
  tuz owner, not left in the pit.
- Win at 82+ kazan stones (bare majority of 162), detected immediately after
  a capture.

Two things RULES.md explicitly flags UNVERIFIED are **not** encoded as fact,
per the "mark UNVERIFIED, don't guess" instruction:
- No stone-count threshold to declare a tuz (the "3 stones" figure is
  Kazakh-sourced, not confirmed Kyrgyz).
- No "starvation sweep" when a player has no legal move — the engine reports
  a distinct `no-legal-moves` result instead of inventing who the remaining
  board goes to. This needs a cultural reviewer or a primary-source ruleset
  before it's safe to encode.

One design decision I made and flagged in a code comment rather than treating
as obvious: if the sowing lap's *last* stone lands in a tuz pit, only the tuz
capture applies — the separate even-count capture rule doesn't also fire on
top of it (a tuz pit's count never accumulates, so "the pit's new total" isn't
a meaningful thing to check there). This isn't stated either way in RULES.md;
it's the reading that avoids a nonsensical double-capture, not a sourced fact.

**Not built this pass, and why**: a playable board UI for Тогуз коргоол
(pits, sowing animation, tuz declaration interaction, local pass-and-play for
2 players since there's no AI opponent or multiplayer backend anywhere in
this app). The engine is real and fully tested, but nothing renders it yet —
same state as the other 9 not-yet-built games, just with working logic behind
it now instead of only a RULES.md. Building the board UI is the natural very-
next task; I stopped here rather than rush a UI in the same pass that also
had to cover the full audit, given how large this session already is.

**Bug fix**: `GameCard.tsx` — the 10 games without a route now show a
"Жакында" badge and a disabled button instead of a live-looking "Ойноо"
button that silently did nothing. Small, but it was the one actual UX bug
Step 2 turned up.

**Housekeeping**: found and killed ~15 orphaned Metro/Node processes (each
~400MB) left over from dev servers started earlier in this session that
weren't fully cleaned up — this is very likely what caused `tsc --noEmit` to
OOM-crash mid-audit. Not an app bug, but worth knowing if this recurs.

## Final summary

### What was fixed
- Dead "Ойноо" buttons on 10 of 11 games in the Games hub (no route → no
  feedback at all) now show a disabled "Жакында" state instead.
- Cleaned up ~15 orphaned high-memory Node processes from earlier dev-server

### What was newly built
- Full Тогуз коргоол rules engine (`games/toguzKorgool/`), 26 passing tests
  covering legal-move validation, sowing/wrap-around, the capture rule, the
  tuz mechanic (including its two exclusion rules and the immediate-sweep
  behavior), win-condition detection, and no-legal-moves detection.
- This audit document itself, and the section-number recovery table at the
  top (grepped from prior sessions' own code comments, since the master spec
  document isn't in the repo).

### What I was NOT confident enough to build automatically — needs your call

1. **The master spec document itself isn't recoverable.** I don't have
   Section 46's literal task list, or exact section numbers for Culture,
   Profile, Onboarding, or the shared-systems sections. Everything I built or
   prioritized this pass used feature-area judgment plus the *fragments*
   recoverable from code comments and `RESEARCH_SUMMARY.md`. If you have the
   source doc, sharing it lets me re-key this whole audit to match it exactly
   and confirms I'm not missing an entire section I don't know exists.

2. **No real shared state anywhere in the app.** XP, coins, achievements,
   streaks, quest progress, collection counts — all of it is hardcoded mock
   data in every screen (Home, Games, Explore, Culture, Profile). This is
   arguably the single biggest foundational gap in the codebase — bigger than
   any one missing game or screen, since fixing it makes every "🟡 PARTIAL"
   screen above become real without much UI rework. I did **not** attempt to
   design and build this speculatively, because it's a real architecture
   decision (local-only vs. eventually backend-synced, what exactly gets
   persisted, whether it needs to survive a reinstall) that affects the whole
   app and deserves your input on shape before I commit to one.

3. **Кыз куумай's "kiss" resolution.** `RESEARCH_SUMMARY.md` already flagged
   this precisely: the traditional resolution needs an explicit non-literal
   treatment for an all-ages app. This is a product/sensitivity decision, not
   a research gap — I did not implement this game's engine at all this pass,
   partly because it's next in priority and partly because I didn't want to
   guess at how to handle this respectfully without your explicit direction.

4. **Жаа атуу has no real ruleset to build from** — only historical archery
   terminology was found, no modern distances/scoring/equipment. This needs a
   dedicated research pass (not implementation work) before any engine code
   should be written for it.

5. **Ордо's piece-count arithmetic is internally inconsistent in the only
   source found** (68 vs. 70) — the authoritative PDF returned HTTP 403 to
   automated fetching. Someone with normal browser access retrieving that PDF
   would resolve this cleanly; I didn't want to pick one number and present it
   as sourced fact.

6. **Ак терек — көк терек and Жоолук таштамай** each have one real open
   rules question flagged in their RULES.md (breakthrough success/failure
   resolution; exact forfeit condition) that need a cultural reviewer, not
   more searching — same category as above, listed for completeness.

7. **Profile screen's visual QA against the design reference is incomplete**
   — not a content/decision gap, just an honest flag that the pixel-level
   check Explore and Culture got never happened for Profile, because the
   browser tool got stuck for the rest of this session (confirmed
   environment-level, not code-level, by retrying after killing the orphaned
   processes above and still hitting the same failure on a plain Home-screen
   load). Worth a manual look when you get a chance.

8. **Onboarding/Auth (spec Section 2) doesn't exist at all** — not flagged as
   a decision exactly, but calling it out because so much *other* code
   (CharacterSelectScreen, TodayDiscoveryCard's guest hint, the whole
   guest-vs-account concept) is written assuming this flow exists and routes
   into it. It's the most obvious "next foundational piece" after the shared
   state question above, if you want a recommendation.
